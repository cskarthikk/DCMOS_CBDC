# First broad evaluation of the Figure 1 candidate

Dataset: `measurements/run_5b97cf3273a1484c8f8a4e6621df6989.csv`. Candidate: `build_internal_matched_v2/candidate.bit`. Metadata records the matching bitstream hash EA95455975095342B43FBEDF5592B7CC4592D20A0E328B1E9C795A5C516AB8E6 and operator confirmation. No independent FPGA firmware identification was performed.

Validated: 5120 accepted rows; 256 distinct odd-parity challenges; trial IDs 1..20 exactly once per challenge; binary responses; expected 21 status marker; no invented activity measurements. This is the first broad run of this architecture, not another original-baseline repeat.

## Observed behavior

- 1204 ones / 5120 responses = **23.515625% ones**, 76.484375% zeros.
- 245 challenges constant in this run: 56 always one and 189 always zero.
- 11 challenges mixed. Their ones counts out of 20: 48A4=2, 146E=18, E468=1, F01A=1, 7798=18, 3818=2, 37A6=3, E6DE=1, 95F4=10, 58D7=17, 6A25=11.
- 95F4 has no strict majority (10/20); 6A25 has a narrow majority (11/20).
- Sum of smaller response counts = 36; the tie contributes 10. This is a sample statistic, not a certified error rate.
- All eight smoke-test challenges remained constant with the same bits in this collection.

## Comparison on identical challenges

The original dataset contains both parity groups; the candidate uses odd parity only and extends the challenge set. A direct comparison of 23.52% with the original all-parity 28.85% mixes design and challenge-set differences. There are 126 shared challenges, all odd parity, with 20 readings per challenge in each design:

| Statistic | Original, shared set | Candidate, shared set |
|---|---:|---:|
| Responses | 2520 | 2520 |
| Ones | 738 | 682 |
| Ones percentage | 29.2857% | 27.0635% |
| Constant challenges | 121 | 122 |
| Mixed challenges | 5 | 4 |
| Sum of smaller response counts | 16 | 6 |
| Majority ties | 0 | 0 |

53 of 126 shared challenge majorities differ across the designs. These are different implementations; this count is not temporal unreliability. Several logic and physical features changed, so the comparison does not isolate a cause. Current evidence supports closer agreement with selected Figure 1 details and somewhat lower observed within-run variation on the shared set, but **does not establish improved balance or general reliability**. The output still favors zero strongly.

## Decision

Retain this candidate and its complete dataset as a measured development checkpoint. Do not call it unbiased, final, or a numerical reproduction of the paper. Stop unchanged-candidate collections for now: the next development issue is the remaining physical asymmetry in launch, cross-feedback, and arbiter-boundary connections. The verified equality of 64 internal signal-net arcs does not extend to these boundary nets or to LUT delays.

The existing modeled SLOW_MAX differences are 278 ps at launch, 210 ps for cross-feedback, and 67 ps into the arbiter D/C terminals. These are implementation estimates, not measured explanations of the observed bias. Any next physical variant must retain this candidate's logical architecture and challenge list, preserve this bitstream, export before/after boundary delays, and be evaluated with a bounded hardware comparison. It must not be selected solely because one sample happens to approach 50% ones.

Full framework expansion remains a later phase, after documenting the accepted single-core architecture and unresolved gate/mapping ambiguities. Hashing or selecting known outputs to force a 50% dataset would not establish raw bias correction.

The PowerShell analyzer and an independent Python calculation reproduced the statistics above. The analyzer now saves shared-set balance and mixed-challenge counts automatically, and handles missing activity instrumentation and ties explicitly.
